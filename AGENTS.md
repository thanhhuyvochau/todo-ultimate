# AGENTS.md

This file defines the high-level application rules, user experience principles, workflow specifications, and guidelines for building the AI Task & Performance Planner application.

For database schemas, TypeScript interfaces, IPC channel specifications, and DeepSeek API prompts, refer to TECHNICAL_SPEC.md.

## 1. Product Vision & Principles

The application is a local-first desktop productivity environment built on Electron. It bridges structured task tracking with personalized AI scheduling and performance coaching.

### Core UX Principles

- **Local-First & Offline Capable**: Tasks, rich notes, time logs, and rules must function without network dependency. Only DeepSeek API interactions require internet access.
- **Non-Intrusive Guidance**: The AI assists, proposes, and analyzes, but the user retains total control over accepting, modifying, or rejecting task plans.
- **Privacy & Security First**: API keys must be encrypted locally using native OS security vaults (`safeStorage`), never written to disk unencrypted or sent to external servers other than the configured AI provider.

## 2. Key Workflow Rules

### Rule 1: Backlog & Task Management

- Every task begins in the Backlog unless auto-generated by a recurring rule or manually assigned to Today.
- Tasks support rich Markdown notes (formatted checklists, code blocks, links).
- Every task requires an initial Time Estimate (in minutes/hours) and a Priority (`low`, `medium`, `high`).

### Rule 2: Recurring Task Rules

- Recurring tasks (e.g., daily reading at 8:00 PM) are defined as Templates, not pre-populated future task instances.
- A background check runs on app startup / date change to instantiate today's task from active rules.
- Recurring tasks with a fixed time anchor (e.g., 20:00) serve as non-negotiable fixed blocks during AI daily scheduling.

### Rule 3: Daily AI Planning ("Morning Standup")

- The user provides daily constraints (available focus hours, primary goal).
- The AI evaluates backlog tasks, fixed recurring commitments, and historical estimation accuracy (Actual / Estimated).
- The AI generates a proposed daily plan with scheduled times and time budgets.
- The user reviews, adjusts, and approves the proposal before tasks transition to the Today view.

### Rule 4: Precision Time Tracking

- Activating a task in the In Progress state triggers the background-safe timer.
- Actual duration is computed from start/pause intervals (`task_time_logs`), preventing timing drift when the window is minimized or closed.
- Variance metrics (Δ = Actual − Estimated) feed back into the AI to continuously refine estimation accuracy.

### Rule 5: On-Demand Performance Review

- Clicking "Generate Performance Report" gathers completed and active tasks for a chosen timeframe.
- The AI computes variance ratios, pinpoints underestimation patterns by priority/type, and delivers structured advice.
- Reports are cached locally for historical reference.

## 3. Development & Architecture Guidelines

- **Process Separation**: Strictly enforce Electron process separation:
  - **Main Process**: SQLite operations, native OS safe storage, background timer logs, recurring task engine.
  - **Renderer Process**: React components, state management, TipTap markdown editing, user interaction.
  - **IPC Communication**: All main-renderer communication must pass through strongly typed IPC handlers using Electron's `contextBridge` and `preload.ts`.
- **Data Integrity**: Never auto-delete unfinished tasks or reset accumulated timer data. Unfinished tasks remain in their current state or backlog without forced rollover.

## 4. Build / Lint / Test Commands

> **Note**: The toolchain below is the recommended target. Verify against `package.json` when available; commands may differ.

```bash
# Install dependencies
npm install

# Start the Electron app in development (hot reload for renderer)
npm run start          # or: npm run dev

# Type-check (both main and renderer)
npm run typecheck

# Lint (ESLint + Prettier)
npm run lint           # report only
npm run lint:fix       # auto-fix
npm run format         # prettier --write

# Build for production
npm run build          # compiles TS + bundles renderer
npm run package        # electron-builder distributable

# Run ALL tests
npm test

# Run tests once (watch mode)
npm run test:watch

# Run a SINGLE test file
npx vitest run src/main/services/__tests__/scheduler.test.ts

# Run a single test by name filter
npx vitest run -t "creates daily plan"

# Run tests with coverage
npm run test:coverage
```

### Test Conventions

- Tests are colocated as `*.test.ts` next to source, or under `src/**/__tests__/`.
- Main-process tests mock SQLite in-memory (`:memory:`) via `better-sqlite3`.
- IPC handlers are tested by invoking the underlying service function directly, not through Electron.

## 5. Code Style Guidelines

### Imports & Modules

- Use ES modules and `import`/`export` exclusively; no `require`.
- Use **named exports** over default exports for all modules and React components.
- Keep import groups separated and ordered: built-in → external packages → local modules.
- Avoid deep relative imports (`../../../../`). Use the configured path alias (e.g., `@/` → `src/`).
- Import only what you use; no unused imports (enforced by ESLint).

### TypeScript & Types

- `strict: true` and `noUncheckedIndexedAccess` are required. No `any` unless absolutely unavoidable (with a documented reason).
- Define a `type` or `interface` for every domain model (Task, TimeLog, RecurringRule, DailyPlan, PerformanceReport).
- Domain models and IPC payload types live in a shared `src/shared/` module imported by both processes.
- Prefer `interface` for object shapes, `type` for unions, aliases, and function signatures.
- Use `satisfies` to validate constants against a type without widening.
- No floating promises: await them or attach a catch handler.
- Type all IPC channels with a shared `IpcChannelMap` so both `ipcMain.handle` and `invoke` are checked.

### Naming Conventions

- React components, hooks, classes, and types: `PascalCase` (`TaskCard`, `useTaskTimer`).
- Functions, variables, and methods: `camelCase` (`getActiveTimer`).
- Constants and enum values: `UPPER_SNAKE_CASE` (`TaskStatus.IN_PROGRESS`).
- SQL tables and columns: `snake_case`; map to camelCase TypeScript via the ORM/row mapper.
- Files: `kebab-case` for modules (`task-scheduler.ts`), `PascalCase` for component files (`TaskCard.tsx`).
- IPC channel names: dot-scoped namespacing (`tasks:getAll`, `timer:start`, `report:generate`).
- Booleans read as questions: `isComplete`, `hasRecurringRule`, `canStart`.

### Error Handling

- Use a shared `AppError` type with a `code` (stable machine-readable string) and `message` (user-facing).
- Never swallow errors with empty `catch {}`. Log, wrap with context, and rethrow.
- In the main process, IPC handlers should return `{ ok: true, data } | { ok: false, error }` and never throw across the bridge.
- Guard state transitions: reject illegal transitions (e.g., `TODO → COMPLETED`) with a descriptive error.
- Validate external input (API responses, IPC args) with runtime checks before use.
- Never log API keys, tokens, or task note contents containing secrets. Sanitize all log output.
- safeStorage encryption failures must fail loudly with a clear user-facing message, never fall back to plaintext.

### React / State

- Use functional components and hooks only. No class components.
- Prefer small, composable components; extract repeated UI into shared components.
- Use `useMemo`/`useCallback` only where perf or reference stability matters; don't wrap everything.
- Keep API/IPC calls in hooks (e.g., `useTasks`) or service modules, not inline in render bodies.
- Store derived state, not mirrored state; compute from source of truth.

### Database (Main Process)

- Use `better-sqlite3` with WAL mode; all access via a single typed repository module per entity.
- Wrap write operations in transactions where atomicity matters (e.g., applying a daily plan).
- Timestamps are stored as Unix epoch milliseconds (integers); use `Date.now()` consistently.
- Time estimates and actual durations are stored in **minutes** as integers.
- Never execute raw interpolated SQL; use prepared statements with parameters only.
- Schema changes go through numbered migrations, applied in order on startup.

### AI Integration (DeepSeek)

- All AI calls go through a single `deepseekService` module; no scattered HTTP calls.
- Timeouts and retries (with backoff) are mandatory on API calls; surface failure to the user non-blockingly.
- Prompts live in `src/main/services/prompts/` and are versioned; never inline prompt strings in components.
- Responses are validated against an expected shape; on parse failure, return a structured fallback rather than crashing.
- Cache AI results (e.g., reports) locally; tag cache entries with timestamps and the prompt version used.

### Formatting

- 2-space indentation, single quotes, trailing semicolons, 100-char print width (Prettier defaults unless overridden).
- Run `npm run format` before committing.

## 6. Working Agreement

- Do not commit API keys or secrets; keep them out of tracked files entirely.
- Never auto-delete or force-reset user task/timer data, even in cleanup code.
- Every IPC channel, schema change, and AI prompt must be documented in TECHNICAL_SPEC.md.
- When in doubt about a user-experience decision, prefer the least intrusive option: assist, propose, never override the user.
- **Never commit changes to git/repository without explicit user approval.**
- **Ticket Sequencing**: After completing and committing any ticket, the agent MUST suggest the next logical ticket to work on based on `TICKET.md` status tracking, dependency order, and implementation readiness, without waiting for the user to ask.

## Rule 7: Dynamic Documentation Linking

- Whenever a new specification, architectural diagram, skill guide, or workflow document is created (e.g., `TECHNICAL_SPEC.md`, a new skill file, or a CLI protocol):
  - The agent MUST immediately append or update the document's link and a brief 1-line description in the **Links & References** section (Section 7) of `AGENTS.md`.
  - Links must use valid relative Markdown syntax (e.g., [`SKILL_NAME.md`](./SKILL_NAME.md)).
  - Existing links must be preserved and kept organized alphabetically or by logical category.
